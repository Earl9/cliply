# Cliply 性能优化文档

> 文档版本：2.0
>
> 对应应用版本：0.4.1-beta.10
>
> 基线与验收日期：2026-08-14
>
> 当前状态：P0–P3 已实施并完成主要验证

本文档记录 Cliply 本轮性能优化的目标、实现、量化结果和后续维护要求。内容以已落地代码和实际测试结果为准，不再作为单纯的优化提案使用。

## 1. 优化结论

本轮优化覆盖主界面渲染、剪贴板事件、滚动合成、同步导出、后台调度、SQLite 维护和前端分包。

| 优先级 | 优化项 | 状态 | 主要结果 |
| --- | --- | --- | --- |
| P0 | 历史列表虚拟化与渲染隔离 | 已完成 | 1,000 条记录时常规视口仅保留约 23 个列表行节点 |
| P0 | 剪贴板变更增量更新 | 已完成 | 普通复制、固定、删除和粘贴成功后不再无条件刷新完整列表 |
| P1 | 自定义滚动条帧同步 | 已完成 | 滚动位置每帧最多更新一次，不再由高频滚动事件触发 React 重渲染 |
| P1 | 收敛重复 CSS 模糊 | 已完成 | 保留 Windows Acrylic，主工作区只在搜索框保留一处小面积模糊 |
| P2 | 同步关联数据批量查询 | 已完成 | 消除格式和标签查询随记录数按 `2N` 增长的问题 |
| P2 | 自动同步调度器事件唤醒 | 已完成 | 由 250 ms 轮询改为条件变量等待，可立即停止并回收线程 |
| P3 | SQLite 查询计划维护 | 已完成 | `PRAGMA optimize` 最多每 7 天执行一次 |
| P3 | 冷路径代码分包 | 已完成 | 主 JavaScript gzip 由 110.25 KB 降至 89.77 KB |

核心验收结果：

- 1,000 条记录连续滚动平均约 59.99 FPS；
- 2 秒内滚动 12,000 px，未检测到主线程长任务；
- 快速输入 10 个字符时，已有可见列表节点全部复用；
- 860 × 560 最小窗口无横向或纵向页面溢出；
- TypeScript、生产构建、Cargo 检查、Clippy 和 Rust 测试均通过；
- 现代独立安装包与 NSIS 备用包均已成功构建。

## 2. 优化范围与边界

### 2.1 本轮覆盖范围

- React 搜索、历史记录列表、详情区域和自定义滚动条；
- Windows Acrylic 与 WebView CSS 毛玻璃的合成成本；
- Tauri 剪贴板监听、事件传递和前端状态更新；
- SQLite 查询计划与低频维护；
- 同步包生成、关联数据加载和后台同步调度；
- 设置、关于等低频界面的代码分包；
- 空闲 CPU、内存、磁盘 I/O、前端包体和安装包构建。

### 2.2 保持不变的产品约束

- 保留无侧边栏的主界面结构；
- 保留年轻化配色、半透明材质和 Windows Acrylic；
- 不缩短历史记录上限来规避列表性能问题；
- 不改变同步队列、墓碑保留、冲突合并和完整快照语义；
- 不直接删除尚未完成同步的墓碑或同步事件；
- 压力测试不向用户真实数据库写入测试数据；
- 不以高频日志作为常驻性能监控方式。

## 4. P0：主界面热路径

### 4.1 历史列表虚拟化

历史列表已改为固定高度虚拟化：

- 列表行内容高度为 68 px，行节距为 76 px；
- 上下 overscan 为 8 行；
- DOM 仅保留可视区域及 overscan，不再渲染全部历史记录；
- 使用稳定记录 ID 作为 key；
- 键盘选择变化时，目标记录会自动滚入视口；
- 当前选择、右键菜单、双击粘贴和固定操作保持原有行为。

### 4.2 渲染边界与节点复用

- `ClipboardList`、`ClipboardListItem` 和 `ClipboardDetailPane` 使用 `memo`；
- 列表行使用稳定的 ID 回调，移除父组件为每行创建的闭包；
- 虚拟位置以数值 offset 传入，避免新建 `style` 对象破坏 `memo` 的浅比较；
- 行级操作通过稳定回调桥接，选择项变化不会更换全部可见行的操作函数；
- 相对时间统一按分钟批量刷新，不为每行建立独立计时；
- 搜索输入变化时，未变化的列表节点可直接复用；
- 设置和关于对话框只在打开时挂载，不参与主界面日常渲染。

### 4.3 剪贴板增量更新

剪贴板监听新增 `clipboard-item-upserted` 事件，并携带完整的 `ClipboardItemDto`。前端据此处理常见单项变化：

- 新记录直接插入正确位置；
- 重复记录更新时间并移动到正确位置；
- 固定状态在本地修补后重新排序；
- 删除记录直接从列表移除并调整选择项；
- 复制和粘贴成功后不再无条件重新查询完整列表。

完整刷新与过滤刷新使用独立 token。同步导入、批量清理、历史上限变化等全局变化仍可触发完整刷新，以保证最终一致性。

后端删除命令不再额外发送一次重复的完整失效事件，避免同一操作造成两次刷新。

## 5. P1：滚动与视觉合成

### 5.1 自定义滚动条

`OverlayScrollArea` 已完成以下调整：

- 使用单个 `requestAnimationFrame` 合并同一帧内的滚动更新；
- 高频 `scrollTop` 和 `thumbTop` 保存到 ref；
- 滑块位置通过 `transform` 直接更新；
- React state 只保留尺寸和可见性等低频状态，尺寸未变化时不调用 state setter；
- `ResizeObserver` 仅在挂载时建立，不再依赖 `children` 引用反复重建；
- 滑块拖动同样按帧合并。

### 5.2 毛玻璃与模糊层级

- 保留 Windows 原生 Acrylic 作为主背景材质；
- 移除整窗、工具栏、双栏和内容面板的重复 CSS 模糊；
- 使用半透明表面、边框和阴影维持界面层级；
- 当前主页面仅搜索框保留一处 `blur(14px)` 小面积模糊；
- 减少透明度和高对比度模式继续优先保证文字与控件清晰度。

该调整减少了 WebView 对大面积背景的重复采样，同时保留现有半透明视觉方向。

## 6. P2：同步与后台调度

### 6.1 同步导出批量查询

同步包生成不再为每条记录分别查询格式和标签：

- 按每 200 个记录 ID 分块批量查询；
- 使用映射结构将格式和标签回填到同步项目；
- 消除每条记录额外执行两次 SQL 的 `2N` 查询模式；
- 每项仍只保留排序后的前 20 个格式；
- 墓碑、pending、abandoned、synced 和完整快照语义保持不变。

已增加批量格式、批量标签和排序测试，确认优化前后的同步字段与业务顺序一致。

### 6.2 自动同步调度器

调度器由每 250 ms 主动轮询改为 `Condvar::wait_timeout`：

- 等待期间不再每秒唤醒约 4 次；
- 停止信号到达时立即通知工作线程；
- `Drop` 阶段等待并回收工作线程；
- 保留初始延迟、60 秒周期和失败指数退避；
- 不改变远端提供方和自动同步开关行为。

## 7. P3：数据库维护与代码分包

### 7.1 SQLite 查询计划维护

- 数据库服务最多每 7 天执行一次 `PRAGMA optimize`；
- 最近执行时间保存于 `sync_state.database_last_optimized_at`；
- 不强制指定索引，不增加重复索引；
- 避免在每次启动或每次查询时执行维护命令。

该策略允许 SQLite 按实际数据分布维护统计信息，同时避免形成持续磁盘写入。

### 7.2 冷路径代码分包

- 设置对话框改为 `React.lazy`；
- 关于对话框改为 `React.lazy`；
- 对话框仅在实际打开时挂载；
- `@tauri-apps/api/event` 统一为静态导入，无效动态导入提示已消失。

## 9. 磁盘与数据库安全

本轮检查未发现软件在空闲状态持续读写硬盘。以下机制用于控制长期写入：

- 剪贴板仅在内容变化时写入；
- 自动同步等待期间不进行 250 ms 轮询；
- 同步失败继续使用指数退避；
- `PRAGMA optimize` 最多每 7 天执行一次；
- 已删除记录作为同步墓碑保留，只有满足同步与保留期条件后才允许硬删除；
- 尚未同步或仍可能参与冲突合并的记录不能直接从数据库物理删除；
- 压力数据只在开发环境内存中生成。

墓碑数量较多主要影响数据库体积和同步快照准备时间，不代表数据库正在持续写入。墓碑清理必须服从同步确认和保留期规则，不能以减少磁盘占用为由破坏多端删除一致性。

## 12. 后续维护建议

以下项目不阻塞本轮完成，可作为后续版本的持续优化项：

1. 在 5,000 和 10,000 条有效记录的测试数据库中复测 SQLite 查询计划；
2. 在远端不可用场景进行 30 分钟以上的 CPU、网络和磁盘采样；
3. 在 120 Hz、高 DPI 和多显示器环境补充滚动与缩放测试；

5. 正式发布前完成安装包签名，并更新发布清单中的大小和 SHA256；
6. 每次调整列表行高、间距或最小窗口尺寸时，同步复测虚拟列表计算和键盘滚入视口行为。
